**1. [HIGH] 정적 분석 실현성: 인터페이스 DI 및 Lombok 구현체 추적 누락**
- **(a) 문제**: Spring 의존성 주입 패턴(인터페이스, Lombok)을 단순 파일명 매칭으로 추적하면 핵심 비즈니스 로직 토큰이 누락됨.
- **(b) 근거**: 설계 2.2절은 1-hop 탐색 시 필드 타입명으로 소스 파일명을 매칭한다고 정의함. 그러나 Spring 실무에서는 `UserService` 같은 인터페이스를 주입받고 `@RequiredArgsConstructor`를 사용하는 것이 표준임. 이 방식을 그대로 적용하면 내용이 없는 인터페이스 시그니처만 스캔되고 실제 로직(토큰)이 담긴 `UserServiceImpl` 구현체가 누락되어 w_i(엔드포인트 작업량)가 심각하게 과소평가됨.
- **(c) 구체적 수정 제안**: 1-hop/2-hop 탐색 시 필드 타입이 인터페이스인 경우 동일 패키지나 하위의 `*Impl.java`를 찾아 병합하는 폴백 로직을 추가하고, Lombok 묵시적 주입(final 필드)도 추출 대상에 포함하도록 파서를 개선하라.

**2. [HIGH] 모델링 타당성: 엔드포인트당 턴 수(τ)의 상수 가정에 따른 2차 비용 과소평가**
- **(a) 문제**: 비용 지배 요인인 턴 수(τ)를 상수로 취급하여 복잡한 프로젝트의 cache_read 비용을 정확히 예측하지 못함.
- **(b) 근거**: `scaling-analysis.md` 2절에 따르면 단일 세션 비용은 턴당 늘어나는 컨텍스트 누적 때문에 2차 함수(quadratic)로 폭증함. 복잡도(w_i)가 큰 엔드포인트는 분석 및 디버깅에 필연적으로 더 많은 턴을 소모하게 됨. 그러나 2.3절의 수식 `reads_i = τ · (C_현재 + w_i/2)`는 τ를 중앙값(8.8 등)으로 고정하여 계산함. 이는 무거운 엔드포인트의 총비용을 심하게 과소평가하는 결과로 이어짐.
- **(c) 구체적 수정 제안**: τ를 상수가 아닌 엔드포인트 복잡도에 비례하는 함수 `τ_i = τ_base + β · (w_i / w̄_cal)` 형태로 재설계하여, 코드가 크면 턴 수도 늘어나는 현실을 모델링하라.

**3. [HIGH] K* 산출 로직: 고정 K 그리드 서치와 가변 Bin-packing의 논리적 충돌**
- **(a) 문제**: 고정 K(개수) 기준의 그리드 탐색과 '컨트롤러 친화적 배정'이 서로 상충하여 비용 최적화를 훼손함.
- **(b) 근거**: 2.4절은 K(엔드포인트 수)를 1~K_max로 고정하여 시뮬레이션한다고 명시하면서, 동시에 청크 배정 시 '컨트롤러 친화 우선(greedy bin-packing)'을 사용한다고 함. 컨트롤러마다 보유한 엔드포인트 수가 제각각이므로, 컨트롤러를 통째로 묶어 컨텍스트 상각 이득을 취하려면 청크마다 K가 가변적이어야 함. 고정 K로 그리드 서치를 강제하면 컨트롤러가 무의미하게 쪼개져 비용 추정이 어긋남.
- **(c) 구체적 수정 제안**: K(개수) 기준의 그리드 서치를 폐기하고, '청크당 목표 누적 컨텍스트 W_target'을 파라미터로 그리드 서치하라. 컨트롤러 단위의 그룹핑을 유지하되 단일 컨트롤러의 누적 w_i가 W_target을 초과할 때만 예외적으로 분할하는 가변 K bin-packing으로 수정하라.

**4. [HIGH] 검증 계획: Hold-in(순환 참조) 검증의 한계 및 교차 검증(Hold-out) 누락**
- **(a) 문제**: 캘리브레이션 훈련 데이터로 오차를 검증하는 순환 참조 구조로 인해 도구의 일반화 능력을 입증할 수 없음.
- **(b) 근거**: 4.1절의 후방 검증(hold-in)은 파라미터를 피팅한 SmartPlant 데이터를 그대로 사용하여 예측 오차가 ±40% 이내인지 검사함. 이는 단순 산술 피팅 검사일 뿐이며, kn-estimator의 핵심 목적인 '타 프로젝트에서의 모드/모델 간 비용 역전 올바른 예측' 타당성을 전혀 증명하지 못함.
- **(c) 구체적 수정 제안**: nimbus 저장소의 다른 샘플 프로젝트나 SmartPlant의 절반을 Hold-out 셋으로 격리하여, 미지의 데이터베이스에서도 모드별 비용 순위(순서 보존)가 유지되고 예측 범위 안에 들어오는지 평가하는 교차 검증 항목을 추가하라.

**5. [HIGH] 누락 리스크: 벽시계 시간(Wall-clock time) 산출식 및 병렬화 트레이드오프 누락**
- **(a) 문제**: 출력 요구사항에 명시된 '예상 벽시계 시간' 산출 로직이 2.3절에 없으며, 실행 구조(순차/병렬)에 따른 비용 차이가 누락됨.
- **(b) 근거**: 2.5절 보고서 항목에는 "예상 벽시계"가 포함되어 있으나 산출 수식이 없음. 또한 `scaling-analysis.md` 4.1절은 청크를 병렬 실행하면 시간은 1/청크 수로 단축되나, 세션 간 공유 캐시가 깨져 청크마다 프리픽스를 독립적으로 `cache_write` 해야 하므로 비용이 증가한다는 중대한 트레이드오프를 명시했으나 비용 모델에 전혀 반영되지 않음.
- **(c) 구체적 수정 제안**: 비용 모델에 `시간 = Σ(API 응답 지연 + 생성 토큰/속도) × τ_i` 수식을 명시하라. CLI 옵션에 `--parallel` 모드를 도입하고, 병렬 선택 시 벽시계 계산법을 `max(청크별 시간)`으로 변경하는 한편 프리픽스 `cache_write` 비용을 청크 수만큼 할증 처리하라.

**6. [MEDIUM] 정적 분석 실현성: MyBatis XML 식별 불가에 따른 토큰 누락 리스크**
- **(a) 문제**: Java 타입 의존성 추적만으로는 2-hop MyBatis 매퍼 XML을 찾을 수 없어 DB 상호작용부 복잡도 추정이 누락됨.
- **(b) 근거**: 2.2절은 2-hop 추적 대상에 "mapper XML"을 포함시켰으나, Spring MyBatis 생태계에서 매퍼 인터페이스는 소스 코드에서 XML 파일명을 직접 참조하지 않고 네임스페이스 규칙으로 암묵적 매핑됨. 제안된 단순 파일명 매칭으로는 방대한 SQL 쿼리 로직이 담긴 XML 파일의 토큰을 결코 찾을 수 없음.
- **(c) 구체적 수정 제안**: 2-hop 스캔 시 `@Mapper` 인터페이스를 발견할 경우, 해당 인터페이스의 패키지 경로 및 네임스페이스와 일치하는 `.xml` 파일을 `src/main/resources/...`에서 역산하여 찾아 합산하는 전용 매핑 룰을 명시적으로 추가하라.

**7. [MEDIUM] 모델링 타당성: 생성 테스트 수(`tests_i`) 도출 로직 부재**
- **(a) 문제**: 출력 토큰 예상 비용(`out_i`) 산출의 핵심 변수인 `tests_i`를 정적 스캔 단계에서 어떻게 알아낼지 정의되지 않음.
- **(b) 근거**: 2.3절 수식 `out_i = out_base + out_per_test · tests_i`는 엔드포인트별 생성 테스트 케이스 개수(`tests_i`)를 요구함. 그러나 LLM을 배제하고 수행하는 2.1, 2.2절 정적 스캐너에는 코드 스펙에서 테스트 개수를 수학적으로 추론하는 방법이 전혀 설계되어 있지 않아 산출식 작동이 불가능함.
- **(c) 구체적 수정 제안**: `tests_i`를 `w_i`에 비례하는 값으로 근사(`tests_i = k · w_i`)하거나, 스캐너가 컨트롤러/서비스 메서드의 if/switch 분기문 개수(Cyclomatic Complexity 근사치)를 카운트해 `tests_i`로 활용하도록 스펙을 보완하라.

**8. [LOW] 모델링 타당성: 청크드 flat의 '초기 1회 환경 분석' 세션 비용 누락**
- **(a) 문제**: 파이프라인의 필수 선행 단계인 공통 컨텍스트 생성 비용이 총 시뮬레이션 비용에서 배제되어 있음.
