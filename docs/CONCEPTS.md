# kn-estimator 개념 가이드 (초급 엔지니어용)

이 문서는 kn-estimator를 처음 보는 엔지니어가 **전제 지식 없이** 도구의 구조와
용어를 이해하도록 쓴 설명서다. 수식 유도는 [docs/cost-model-explained.md](cost-model-explained.md),
캘리브레이션 실전 절차는 [docs/CALIBRATION.md](CALIBRATION.md)에 있다.

## 1. 큰 그림 — 이 도구는 무엇을 계산하나

LLM 에이전트에게 "엔드포인트 100개의 테스트를 만들어줘" 같은 **반복 작업**을
시키면, 한 세션 안에서 대화를 이어갈수록 컨텍스트(대화 기록)가 쌓여 뒤로 갈수록
같은 일에 더 많은 토큰을 낸다 — 비용이 개수 N에 대해 **2차 함수**로 는다.
반대로 몇 개씩 끊어 **새 세션**에서 돌리면 선형이 된다. 그래서 질문은 하나다:

> **몇 개씩(K) 묶어서 돌려야 가장 싼가?**

kn-estimator는 이 K와 "그룹1(…), 그룹2(…)로 돌리세요"라는 실행 계획, 예상
비용을 **LLM 호출 없이** 계산한다. 내부는 두 부분으로 나뉜다:

```
┌─────────────── 앞단 (front-end) ───────────────┐   ┌────────── 뒷단 (back-end) ──────────┐
│ "무엇이 몇 개 있고(N), 각각 얼마나 큰가(w),     │   │ 캘리브레이션 계수 + N·w·group        │
│  어떤 것끼리 묶으면 좋은가(group)" 를 만든다    │ → │ → 최적 K, 벽(context 한계) 제약,     │
│                                                │   │   bin-packing 그룹 편성, 비용·구간   │
│  ① Spring 스캐너  ② --targets  ③ --n           │   │   (plan.py / model.py — 단위 무지)   │
└────────────────────────────────────────────────┘   └─────────────────────────────────────┘
```

핵심 설계 원칙: **뒷단은 "단위"가 뭔지 모른다.** 엔드포인트인지 클래스인지
파일인지 문서인지는 뒷단에 전달되지 않는다 — 개수 N, 상대 크기 w, 묶음 힌트
group만 소비한다. 단위의 의미는 사용자(와 캘리브레이션)만 안다.

## 2. 앞단 3종 — 대상 목록을 만드는 세 가지 방법

앞단의 일은 "대상 목록"을 만드는 것이다. 대상(target) = 반복 작업이 적용되는
단위 하나.

### ① Spring 스캐너 (프로젝트 경로를 주면 자동)

```bash
kn-estimate ./my-spring-app --groups
```

Spring 백엔드의 **JSON 엔드포인트**라는 특정 단위에 특화된 자동 목록 생성기다.
소스를 정적 분석해서:

- `@RestController`/`@ResponseBody` 어노테이션을 훑어 엔드포인트 목록(N)을 만들고,
- 각 엔드포인트가 세션에 끌고 들어올 코드량(w)을 계산한다 — 핸들러 메서드 +
  주입(DI)된 서비스/DAO를 따라가며 + MyBatis XML/JPA 엔티티까지 합산,
- 소속 컨트롤러를 group 힌트로 쓴다 (같은 컨트롤러 = 같은 세션에 묶으면 유리).

즉 스캐너는 "엔드포인트 단위 전용 고급 앞단"일 뿐, 비용 모델의 일부가 아니다.

### ② `--targets` — 목록을 직접 공급 (임의 단위)

어떤 단위든 "한 줄에 하나" 텍스트로 주면 된다. 목록은 셸이 만든다:

```bash
find src -name '*Service.java' > targets.txt
kn-estimate --targets targets.txt --label analyze --model sonnet --groups

ls docs/*.md | kn-estimate --targets - --label translate --model haiku
```

- 줄 전부가 **실존 파일 경로**면: w=파일 크기(bytes/4), group=디렉터리 자동.
- 그냥 이름 문자열이면(클래스명·티켓번호…): w 균일 가정, group 없음.
- 정밀 제어가 필요하면 `.json`:

```json
[{"id": "OwnerController#findOwner", "w": 120, "group": "OwnerController"},
 {"id": "PetController#create", "group": "PetController"}]
```

`w`·`group`은 생략 가능(균일·무그룹). **단위 유형을 적는 필드는 없다** — §6 참고.
주의: stdin(`-`)은 텍스트 목록 전용이다. JSON은 파일로 지정하라.

### ③ `--n` — 개수만 (최소형)

```bash
kn-estimate --n 100 --label analyze --model sonnet
```

"100개짜리 작업인데 몇 개씩 끊지?"만 궁금할 때. 균일 w의 합성 대상 100개로
계산한다.

## 3. w란 무엇인가 — 왜 "상대" 크기인가

w는 **대상 하나가 세션에 끌고 들어올 리소스의 상대적 크기**다. 절대 단위가
없다 — 모델 내부에서 평균으로 나눠(ŵ = w/평균) 비율만 쓰기 때문에, 목록의 w를
전부 10배 해도 결과는 같다(스케일 불변). bytes든 라인 수든 **일관되기만 하면**
된다.

"균일 가정이면 부정확하지 않나?" — 실측(캠페인 §4.7)에서 w는 세션당 비용
분산을 거의 설명하지 못했다(R²≈0). 그 데이터의 단위(엔드포인트)가 비교적
균질했기 때문이기도 하다. 요점:

- **절대 비용의 정확도는 w가 아니라 캘리브레이션 계수가 책임진다** (§4).
- w의 역할은 그룹 편성의 균형(큰 대상이 벽 예산을 더 먹게)과 이상치 감지(§5)다.
- 그래서 w 채우기에 과투자할 필요 없다 — 파일 목록이면 공짜(자동), 아니면
  균일로 충분한 경우가 대부분이다.

| 입력 | w 출처 | group |
|---|---|---|
| Spring 스캐너 | DI 그래프 추적 코드량 | 컨트롤러 |
| `--targets` 파일 경로 목록 | 파일 크기(bytes/4, 최소 1) | 디렉터리 |
| `--targets` 이름 문자열 목록 | 균일(1) | 없음 |
| `--targets` `.json` | 사용자 명시 (생략 시 1) | 사용자 명시 |
| `--n` | 균일(1) | 없음 |

## 4. 캘리브레이션·라벨·셀 — 계수는 어디서 오나

비용 곡선의 계수(청크 고정비 a, 대상당 한계비용 b, 컨텍스트 누적항 c 등)는
**실측에서 온다**. 같은 작업을 크기가 다른 두 묶음(예: 1개짜리 + 5개짜리)으로
실제 실행해 기록한 원장(run_ledger.jsonl)을 `kn-calibrate`가 적합(fit)한다.
이것이 **파일럿 캘리브레이션**이다 — 자세한 절차와 에이전트 지시 템플릿은
[CALIBRATION.md](CALIBRATION.md).

- **라벨(label)**: 작업 종류의 이름표. 자유 문자열이다 — `template`, `analyze`,
  `translate`… "파일을 그대로 복사"와 "코드를 설명"은 단위당 비용 구조 자체가
  다르므로 **다른 라벨로 따로 캘리브레이션**한다.
- **셀(cell)**: `<label>/<model>` 조합 (예: `analyze/sonnet`). 계수는 셀마다
  하나씩이다.
- 자체 캘리브레이션이 없으면 동봉(캠페인 실측) 계수로 **상대 비교용** 추정을
  내고, 그 사실을 고지한다.

## 5. 이상치 감지 — "괴물"이 섞였을 때

목록 안에 나머지보다 **이질적으로 큰** 대상(예: 1만 라인짜리 파일 하나)이
섞이면, 그 셀의 계수로의 외삽은 과소추정 위험이 있다. 툴은 w가 중앙값의
4배를 넘는 대상을 감지해 경고한다:

```
⚠ 이상치 1건: huge_module.py (w=41,000, 12배) — 이 대상들은 나머지와 크기가
이질적입니다. … 별도 라벨로 분리 측정을 권장합니다.
```

- 권장 대응: 괴물들을 목록에서 빼서 **별도 라벨**(별도 파일럿)로 다루거나,
  개별 처리한다. 강제 배치 변경은 하지 않는다 — 경고는 "모델 적용 한계의
  고지"다.
- **균일 w 경로(`--n`, 이름 문자열 목록, w 생략 JSON)에서는 정의상 절대
  발동하지 않는다** — 모든 w가 같으면 이상치가 없다. 크기 이질성을 알리려면
  JSON으로 w를 명시해야 한다.

## 6. 단위 일관성 계약 — 사용자가 지켜야 하는 단 하나

툴은 단위를 모르기 때문에, 딱 하나의 계약을 사용자가 지켜야 한다:

> **파일럿(캘리브레이션)에서 센 n과, 추정에 넣는 목록의 N은 같은 단위로
> 세어져야 한다.**

클래스 단위로 파일럿을 돌려 만든 셀(δ=클래스 1개당 비용)에 메소드 목록을
넣으면 계수가 무의미해진다 — 툴은 이를 검증할 방법이 없다. 라벨 이름에 단위를
담아두면(예: `analyze-class`) 실수를 줄일 수 있다.

같은 이유로, 이름 문자열 목록에서 서로 다른 표기가 같은 대상을 가리키는 중복
(`OwnerController#find`와 `find(OwnerController)`)도 툴이 잡아줄 수 없다 —
목록을 만드는 쪽의 책임이다. (파일 경로 중복 `./a.txt`↔`a.txt`는 잡는다.)

## 7. 요리책 — 단위별 목록 만들기 레시피

추정 파이프라인은 전 단위 공통이고, 단위별로 다른 것은 **목록 생성법뿐**이다:

| 단위 | 레시피 | w | group |
|---|---|---|---|
| 파일 | `find src -name '*.md' > targets.txt` | 크기 자동 | 디렉터리 자동 |
| 클래스 | Java는 1클래스=1파일 관례 → 파일과 동일. 예외(내부 클래스)는 이름 나열 | 자동 or 균일 | 자동 or 없음 |
| 메소드 | `OwnerController#findOwner` 문자열 나열 (ctags/grep으로 추출) | 균일 (원하면 JSON으로 라인 수) | JSON으로 소속 클래스 |
| 엔드포인트 | Spring이면 목록 불필요 — 위치 인자로 스캐너 자동. 비-Spring이면 `GET /owners/{id}` 나열 | 스캐너 계산 / 균일 | 컨트롤러 / URL prefix |
| 티켓·문서·테이블 등 | 어디서든 한 줄에 하나로 뽑으면 됨 | 균일 or JSON | 필요시 JSON |

마지막으로 흐름 전체를 한 번에:

```bash
# ① (정확도가 필요하면) 파일럿: 같은 라벨로 크기 다른 2묶음 실측 → kn-calibrate
# ② 전체 목록 공급 → K·그룹·비용
find src -name '*Service.java' > targets.txt
kn-estimate --targets targets.txt --label analyze --model sonnet \
            --calibration my-cal.json --groups
# → "그룹1(…), 그룹2(…)로 돌리세요" + 예상 비용/구간
```

## 8. 근거 문헌 — "멀티턴 비용은 2차"는 어디서 오는 사실인가

§1의 전제(세션을 이어가면 비용이 N²)는 이 프로젝트의 주장이 아니라, 서로 다른
층위의 문헌·공식 문서가 각각 뒷받침하는 사실이다:

| 층위 | 내용 | 출처 |
|---|---|---|
| 과금 구조 | 매 턴 전체 대화 프리픽스가 입력으로 다시 과금된다 (캐시 히트도 0.1×로 재과금) → 누적 입력 토큰이 턴 수에 2차 | [Anthropic prompt caching 문서](https://platform.claude.com/docs/en/build-with-claude/prompt-caching) |
| 서빙 시스템 | 멀티턴 대화는 역사 토큰의 KV 캐시를 반복 재계산해 서빙 비용이 높다 — 재사용으로 e2e 추론 비용 최대 70% 절감 | [CachedAttention, USENIX ATC'24](https://www.usenix.org/conference/atc24/presentation/gao-bin-cost) ([arXiv:2403.19708](https://arxiv.org/abs/2403.19708)) |
| 계산 복잡도 | self-attention 계산량은 시퀀스 길이에 O(n²) | [Attention Is All You Need](https://arxiv.org/abs/1706.03762) |
| 평가 방법론 | 에이전트는 정확도와 비용을 함께 최적화 대상으로 평가해야 한다 | [AI Agents That Matter](https://arxiv.org/abs/2407.01502) |

읽을 때 층위를 섞지 않는 것이 중요하다:

- 계산 복잡도의 O(n²)는 **한 번의 forward pass** 이야기다. API 과금은 토큰당
  선형이므로, 이 도구가 다루는 2차는 계산 복잡도가 아니라 **매 턴 히스토리
  재전송의 누적**(과금 구조 층위)에서 온다.
- 프롬프트 캐싱을 켜도 2차가 사라지는 게 아니라 **상수가 작아진다** — cache
  read가 0.1×로 재과금되기 때문이다. 이 도구 비용 모델의 P_cache_read 항
  ([cost-model-explained.md](cost-model-explained.md) 수식 유도 참고)이 바로
  그 잔여 2차 항이고, 캘리브레이션이 그 크기를 실측 계수로 적합한다.
