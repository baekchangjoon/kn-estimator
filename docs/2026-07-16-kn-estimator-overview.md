## 1. 배경 — 왜 필요한가

출발점은 **"LLM으로 테스트를 생성하면 비용이 엔드포인트 수에 비례할 것"이라는 직관이 틀렸다**는
실측 발견이다.

단일 LLM 세션에서 엔드포인트를 순서대로 처리하면 두 가지가 **동시에** 자란다:

1. **턴 수 ∝ N** — 엔드포인트마다 분석·작성·확인 턴이 필요하다 (실측 6~10턴/EP).
2. **턴당 읽기 비용 ∝ 누적 컨텍스트** — API는 매 턴 대화 이력 전체를 다시 읽고(cache_read),
   이력에는 앞선 엔드포인트의 도구 결과가 잔류한다 (실측 +16~26K 토큰/EP). 실측에서 52K로
   시작한 컨텍스트가 83턴 뒤 257K가 됐다.

총 read 비용은 곡선 아래 **면적**인데 밑변(턴 수)과 높이(컨텍스트)가 둘 다 N에 비례하니 면적은
N²에 비례한다:

```
총 read ≈ Σᵢ τ·(S0 + δ·i) = τ·S0·N + τ·δ·N(N+1)/2
                            ↑1차항      ↑2차항
```

정리하면 `C(N) = a + bN + cN²` (flat×opus 실측 fit: a≈2.4, b≈0.8, c≈0.02). 귀결이 둘이다:

- **비용**: N 2배 → 4배, 10배 → 100배. 교차점 N≈16부터 2차항이 역전한다.
- **실행 가능성**: N≳36~59부터 1M 컨텍스트 윈도우에 걸려 **아예 못 돌린다**. 비용 이전에 벽이다.

### 1.1 해법 — 청크드 실행이 2차를 1차로 만든다

K개씩 끊어 **독립 세션**으로 돌리면 각 세션이 작은 N=K에 머물러 2차항이 억제되고, 총비용은
`⌈N/K⌉ × C(K)` — N에 비례하는 **1차 직선**이 된다.

주의할 뉘앙스: **2차항이 사라지는 게 아니다.** 2차항이 아직 지배하지 못하는 구간 안에 K를
가둬두는 것이다. 각 청크는 2차 곡선의 싼 앞부분만 잘라 쓰고, 그 조각들을 이어붙인 전체가
직선이 된다.

### 1.2 그래서 K가 1차 설계 변수다

청크드 실행이 만드는 직선의 **기울기**는 엔드포인트당 단가 `g(K)`이고, U자를 그린다:

```
g(K) = C(K)/K = a/K + b + c·K
                 ↑고정비 상각    ↑2차 페널티
                (K↑ 유리)       (K↑ 불리)
```

- **K가 작으면**: 청크마다 고정비 a(62KB 지침 적재, 환경분석)를 재지불. 극단인 K=1
  (per_endpoint)이 실측에서 flat의 **7.9배($80.83)** 였다.
- **K가 크면**: 청크 내부 2차항이 커지고 품질이 무너진다 — 실측에서 게이트 실패가 세션
  후반부에 몰렸다(컴팩션, 지침 망각).
- **균형점**: `K* = √(a/c) ≈ 11`. 품질 여유를 두면 **K=8~12**가 권장 대역.

**핵심:** K는 사소한 실행 옵션이 아니라 비용 직선의 기울기와 품질 리스크를 **동시에** 결정한다.
그런데 계수 a·b·c는 프로젝트마다 다르다. 그래서 착수 전에 프로젝트별로 계산할 도구가 필요하다.

## 2. 목적

**2차 곡선을 싼 조각으로 잘라 1차 직선을 만들고, 그 직선의 기울기가 최소가 되는 조각 크기를
프로젝트별로 미리 계산한다.**

제약이 목적만큼 중요하다 — **LLM 호출 없이, 빌드 없이, 정적 파일 스캔만으로 수 초 내**(CI에서
돌 수 있게). 예측하려고 실제로 돌려보면 예측의 의미가 없기 때문이다.

산출: `kn-report.md`(사람용) + `kn-plan.json`(기계용 청크 플랜).

## 3. 구현 방법

| 모듈 | 역할 |
|---|---|
| `endpoints.py` | 컨트롤러 정규식 스캔 → JSON 엔드포인트 목록 (harness에서 vendored) |
| `scan.py` | 인벤토리(N) + EP별 작업량 `w_i` 정적 슬라이스 |
| `calibrate.py` | 실측 원장 + 트랜스크립트 → 셀별 계수 |
| `model.py` | 청크 하나를 턴 단위로 이산 시뮬레이션 |
| `plan.py` | FFD 청크 파티션 + W_target 그리드 최적화 |
| `cli.py` | CLI (`kn-estimate`) — 위를 엮어 보고서·플랜 산출 |

### 3.1 N — 엔드포인트 인벤토리

`*Controller.java`를 정규식으로 훑어 JSON 핸들러만 채택(`@RestController` | `JSON_VIEW` |
`@ResponseBody`). Spring의 base+sub 경로 조인 버그 수정판이다(`endpoints.py:96-99`).

### 3.2 w_i — 정적 슬라이스

그 엔드포인트를 처리할 때 LLM이 **읽게 될 코드량**을 정적 근사한다:

```
w_i = 핸들러 메서드 span
    + Σ 주입 그래프 2-hop 파일 토큰 (최단 깊이 1 → 감쇠 1.0, 깊이 2 → 0.5)
    + Σ MyBatis XML 토큰
tokens(file) ≈ bytes / 4
```

주입 해석은 `@Autowired` 필드 / 생성자 파라미터 / Lombok `private final`. 인터페이스는 동일
트리 `*Impl` 폴백. **매칭 실패는 조용한 0이 아니라 `unresolved` 플래그 + 프로젝트 중앙값
prior 보정**(`scan.py:152-158`).

### 3.3 캘리브레이션

SmartPlant 실측 run에서 셀(모드×모델)별 **관측 가능량만** 추출: `S0`(첫 턴 컨텍스트),
`τ`(턴 수), `δ`(컨텍스트 잔류 증가), `out`(출력 토큰). 각각을 **env(1회 고정분) / ep(한계분)**
으로 2점 분해한다(N=1, N=8 두 점 fit). 단일 N 셀은 flat/opus의 env:ep 비율을 차용하고
`env_split_approx` 플래그를 남긴다.

규율 둘: **게이트 통과 run만** 쓴다(실패 run은 조기 종료로 비용이 과소해 계수를 오염시킨다),
측정 인프라 위양성은 `gate-adjudications.json`에 명시된 것만 구제한다(`calibrate.py:43-49`).

### 3.4 비용 모델

닫힌식 대신 청크를 **턴 단위로 직접 합산**한다(`model.py:23-37`):

```
cost = P_cr·Σ(τ_i·C_현재) + P_cw·(S0 + Σδ_i) + P_out·Σout_i
```

이는 **요약식**이다. 실제 구현은 두 가지를 더 포함한다 — ①env 고정분(`tau_env`/`delta_env`/
`out_env`)이 청크마다 1회 선가산되고(이는 **정상** — §6.2 K8 참조), ②cache_read는 구간 중점으로
계산된다(`tau_i · (ctx + delta_i/2)`). 정확한 정의는 `simulate_chunk`를 따른다.

`w_i`는 절대 토큰이 아니라 **곱셈 공변량**으로만 쓴다 — `k = (w_i/w̄)^α`, α 기본 0.5
("코드가 2배 커도 읽기가 2배 늘진 않는다").

### 3.4.1 결정적 성질 — 모델은 w에 대해 스케일 불변이다

이 절을 오해하면 개선 우선순위가 통째로 틀어지므로 명시한다. `w_tokens`는 모델에 오직
**`w_tokens / w_mean`**(프로젝트 평균 대비 비율) 형태로만 들어간다(`plan.py:22`, `plan.py:67`).
비용식 어디에도 절대 토큰 항이 없다. 실측:

| 실험 | 결과 |
|---|---|
| 원본 | $143.91, 60청크 |
| **모든 w_i를 2배** | **$143.91, 60청크 — 완전 동일** |
| 모든 w_i에 컨트롤러 토큰 가산 | $141.35, 57청크 (증가가 아니라 **감소**) |

정확히 무엇이 참인지 구분해야 한다 — 이 구분을 뭉개면 반대 방향으로 틀린다.

**참 (2행이 증명):** 청크 비용식에는 **절대 w 항이 없다.** w를 **균일 배수**하면 모든 비율이
그대로라 결과가 **정확히** 불변이다. 절대 크기 자체는 아무 의미가 없다.

**거짓이면 안 되는 것 (3행이 증명):** 그렇다고 "w를 바꿔도 절대 비용은 안 변한다"는 **아니다.**
`w_i`를 **비균일**하게 바꾸면 FFD 파티션이 달라지고 → **청크 수가 달라지고**(60→57) → 청크마다
무는 고정비 `a`를 무는 **횟수**가 달라져 → 절대 비용이 움직인다($143.91→$141.35, 약 1.8%).
즉 w는 **파티션이라는 간접 경로로** 절대 비용에 작용한다.

추가로, `peak_context`(절대 토큰량)가 `w_hard`/`w_soft` 벽과 비교되고(`plan.py:69,72`) 초과 시
1.15배 페널티가 붙는다. 실측에서 `peak_context`가 170~179K로 `w_soft`(180K)에 **바짝 붙어
있어**, 파티션이 조금만 달라져도 페널티 여부가 뒤집힐 수 있다.

**그래서 정리하면:**

- 컨트롤러를 읽는 비용은 **이미 `delta_ep`/`delta_env` 안에 있다** — 그 계수가 컨트롤러를 실제로
  읽은 run에서 fit됐다. 따라서 "w에 컨트롤러 토큰을 더해 비용을 올린다"는 발상은 성립하지
  않는다(3행이 오히려 내려간 이유는 상대 분산이 **압축**돼 분포가 바뀐 것이지 비용 항이 생긴 게
  아니다).
- `w_i` 정확도 개선(복잡도, MyBatis 매칭)의 주 효과는 **상대 순위와 청크 구성**이고, 절대 비용
  변화는 파티션 경로를 통한 **부수 효과**(이 데이터에선 ~1.8% 규모)다.
- **절대 USD 수준 자체는 캘리브레이션 표본(단일 프로젝트 18 run)이 정한다.** 이건 코드로 고칠
  수 없다 — README가 "절대 USD 비보증, 상대 비교용"이라 못 박은 것이 이 구조 때문이다.

### 3.5 청크 플랜

균일 K가 아니라 **컨트롤러 친화 FFD bin-packing**이다(같은 컨트롤러 EP를 묶어 공유 컨텍스트
재활용). 벽이 이층 — `W_hard`(900K, 모델 상한, 위반 불가) / `W_soft`(180K, 품질 정책, 초과 시
1.15배 페널티). W_target을 5개 fraction 그리드로 훑어 총비용 최소를 고른다.

### 3.6 설계상 정직한 부분

- 미캘리브레이션 셀은 추정치를 지어내지 않고 `insufficient_calibration` 표기.
- 예측구간 = α 민감도(좁은 CI) × run 분산 밴드(넓은 CI, 실측 ±30~46%).
- **"절대 USD 비보증"** 을 보고서에 명시 — 단일 프로젝트 캘리브레이션이므로 주 용도는 상대 비교.

## 4. 코드량과 코드복잡도 — 무엇이 반영됐고 무엇이 빠졌나

이 절은 "코드량·복잡도가 비용에 영향을 줄 텐데 반영됐는가"라는 질문에 답한다. **코드량은
반영됐고, 복잡도는 의도적으로 폐기됐으며, 그 폐기가 부채 5건을 남겼다.**

### 4.1 코드량 — 반영됨

`w_i`가 정확히 코드량이다. `tokens_of()`는 `st_size * 1/4`(파일 바이트), 핸들러는
`len((anns+body).encode()) * 1/4`(span 바이트). 이것이 δ(컨텍스트 잔류)의 공변량으로 쓰인다.

### 4.2 코드복잡도 — 측정하지 않음

코드 전체에 복잡도 지표가 **0건**이다(`complexity|cyclomatic|branch|nesting|halstead` grep →
`cli.py:121`의 보고서 제목 문자열 1건뿐). 계산되는 양은 오직 바이트 크기다.

### 4.3 왜 없나 — 추적 가능한 결정이다

원래 설계에는 복잡도 항이 있었다. 설계 문서 §2.3(`docs/2026-07-09-kn-estimator-design.md:53`):

```
out_i = out_base + out_per_test · tests_i
```

`tests_i`(엔드포인트당 테스트 케이스 수)는 복잡도 대리변수다 — 분기가 많으면 테스트가 많아지고
출력이 커진다. 이를 3벤더 리뷰 **K1이 폐기**시켰다(`docs/2026-07-09-kn-estimator-review-triage.md:10`):

> 비용 식 자기모순 (… **tests_i 산출 경로 없음** …) → **관측 가능량만으로 축소**: 셀별
> (S0, τ, δ̄, out̄) + 가격표. w_i는 δ·out의 곱셈 공변량(ŵ^α)으로만. **tests_i 폐기**.

즉 "정적으로 산출할 방법이 없다"가 폐기 사유였다. 누락이 아니라 결정이다.

### 4.4 그 결정이 남긴 부채 5건

| # | 부채 | 근거 |
|---|---|---|
| C1 | **하나의 크기 공변량이 성격이 다른 세 양을 동시에 스케일** | `model.py:31` |
| C2 | 문서는 여전히 "코드 복잡도"가 δ·τ를 움직인다고 주장 — 구현과 불일치 | `docs/cost-model-explained.md:95`, `docs/GUIDE.md:20` |
| C3 | 보고서가 **크기 순위를 "복잡도 상위 10"이라고 라벨** — 용어 오용 | `cli.py:121` |
| C4 | 설계 문서에 폐기된 `tests_i` 공식이 **인라인 표시 없이 잔존** | `docs/2026-07-09-kn-estimator-design.md` 53행 vs 139행 |
| C5 | 한계 고지에 "복잡도 미반영"이 없음 | `cli.py:127-131` |

C4는 **자기모순이 아니다.** `docs/2026-07-09-kn-estimator-design.md:116`이 *"아래 개정이 §2~4의 원문과 충돌하면 개정이
우선한다"* 는 우선순위 규칙을 명시하므로 절차적으로는 이미 해소돼 있다. 남은 건 문서 위생
문제다 — 폐기된 §2.3 원문에 취소선·경과 표시가 없어 초독자가 살아 있는 공식으로 오독한다.

**C1이 가장 중요하다.** `model.py:31`은 이렇게 한다:

```python
k = wh ** alpha
tau_i, delta_i, out_i = c["tau_ep"] * k, c["delta_ep"] * k, c["out_ep"] * k
```

세 양의 드라이버가 서로 다른데 **같은 크기 기반 k**를 받는다:

- **δ (컨텍스트 잔류)** ← 크기가 **인과적으로 맞다**. LLM은 바이트를 읽고, 읽은 바이트가
  이력에 남는다. 여기서는 크기가 대리변수가 아니라 실체다.
- **τ (턴 수), out (출력 토큰)** ← **필요한 테스트 케이스 수**에 좌우된다. 이건 분기 수·
  순환복잡도에 가깝지 크기가 아니다.

같은 300바이트 핸들러라도 CRUD 패스스루는 테스트 1~2개, 15분기 검증 로직은 테스트 15개+가
필요하다. 그런데 현재 모델은 **둘에 동일한 k를 준다.** α=0.5 지수가 이 불일치를 일부 흡수하고
있을 가능성이 있으나(크기→작업량 비선형성을 뭉뚱그림), 그건 보정이지 모델링이 아니다.

**영향 범위:** `wh`는 프로젝트 평균 대비 비율이므로(§3.4.1) C1이 틀어뜨리는 것은 **EP 간 상대
가중치와 청크 구성**이지 절대 비용 수준이 아니다. 복잡도를 반영해도 총액이 "정확해지지"는
않는다 — 총액은 캘리브레이션 표본이 정한다. 개선되는 것은 **어느 엔드포인트가 무거운지의 순위**,
즉 청크를 어떻게 묶을지와 "복잡도 상위 10" 표의 타당성이다. 이 도구의 선언된 주 용도(상대 비교와
청크 플랜)가 바로 그 영역이므로 여전히 유의미하다.

### 4.5 K1의 폐기 사유는 순환복잡도에는 적용되지 않는다

K1이 `tests_i`를 버린 이유는 "산출 경로 없음"이다 — **LLM이 몇 개의 테스트를 쓸지는 미리 알 수
없다**는 뜻이고, 타당하다. 그러나 **순환복잡도는 정적으로 측정 가능하다.** 핸들러 span에서
`if`/`for`/`while`/`case`/`catch`/`&&`/`||`/`?:`를 세면 된다 — 이미 span 텍스트를 손에 쥐고
있으므로(`scan.py:88-92`) 추가 파싱 비용이 사실상 0이다.

즉 **"복잡도는 관측 불가"는 참이 아니다.** 관측 불가였던 건 `tests_i`(미래 산출물)이지
분기 수(현재 코드의 성질)가 아니다. K1의 결론을 분기 수까지 확장 적용하는 건 과잉 일반화다.

### 4.6 지금 데이터로 검증할 수 있는가 — 파이프라인엔 없지만 원자료엔 있을 수 있다

분기 수 공변량이 크기 공변량보다 나은지 확인하려면 **EP별** τ·out 실측이 필요하다.

**현재 파이프라인에는 없다.** 원장은 run 단위이고 `calibrate.py:57-60`이 run별
turns/out/cost를 집계하며, 캘리브레이션은 N=1/N=8의 **집계 2점 분해**다. EP별 관측치가
파이프라인 어디에도 없다.

**그러나 원자료에는 복구 가능성이 있다.** 3벤더 리뷰(Claude 슬롯)가 실측으로 지적했다 —
`results/runs/flat-n8-r1/transcript.jsonl`의 Write 도구 호출이 **run 초기 프롬프트의
엔드포인트 순서와 같은 순서로** 테스트 파일을 생성한다(`MemberQosStatusBlackBoxTest.java`,
`ClientCancelBlackBoxTest.java`, … 8개 목록과 순서 일치). 즉 **연속한 EP 경계 Write 사이로
턴을 분할하면** 새 실험 없이 기존 트랜스크립트에서 EP별 τ·out을 뽑을 수 있을 가능성이 높다.

따라서 경로는 셋이다:

- **즉시(무비용)**: C2~C5를 고쳐 **현재 모델이 크기만 본다는 사실을 명시**한다. 특히 C3의
  "복잡도 상위 10" → "슬라이스 크기 상위 10" 라벨 수정과 C5의 한계 고지 추가. 이건 §6.1
  A단계와 함께 처리 가능하다.
- **근시일(새 run 불필요)**: 위 세그멘테이션 타당성을 조사한다 — EP 경계 Write를 기준으로
  턴을 분할해 EP별 τ·out을 복원하고, `w_i`(크기) vs 분기 수의 설명력을 비교한다. 성공하면
  C1은 **데이터 기반 결정**이 된다.
- **최후(새 실험)**: 세그멘테이션이 불가능하다고 판명될 때만 EP별 관측 가능한 소규모 실험을
  별도 설계한다.

**핵심:** C1을 근거 없이 도입하면 크기 공변량을 다른 미검증 공변량으로 바꾸는 것에 불과하다.
그러나 검증 수단이 이미 손에 있을 수 있으므로, "데이터가 없다"고 단정하고 미루는 것도 틀렸다.

**요약:** 코드량은 δ에 대해 올바르게 반영돼 있다. 복잡도는 τ·out의 진짜 드라이버일 개연성이
높지만 현재 모델에 없고, 없다는 사실이 문서·보고서에 고지되지 않은 채 "복잡도"라는 라벨로
가려져 있다. **가려진 것을 드러내는 것이 1순위이고, 대체 공변량 도입은 검증 수단을 확보한
다음이다.**

**완료됨.** 설계: `docs/superpowers/specs/2026-07-16-kn-estimator-standalone-design.md`.
검증: 설치된 `kn-estimate`가 `N=167 chunks=60 k_avg=2.8 est=$143.91`과 골든 바이트 일치
(`kn-plan.json` `db19bcf9…`, `kn-report.md` `ab230896…`); 신규 클론에서 `results/`를 지워도
동작; `pytest` 13 passed, 1 skipped.

### 6.2 B단계 — 리뷰 잔여 개선 (**대부분 완료 2026-07-16**)

> **정정 이력(2026-07-16):** 이 목록의 초판은 K3(4)와 K8을 결함으로 올렸으나, §3.4.1의 스케일
> 불변성을 실측한 뒤 **둘 다 결함이 아님을 확인**하고 §6.2.1로 옮겼다. 초판은 "컨트롤러 토큰
> 누락 → 비용 체계적 과소추정"을 1순위로 지목했는데, 모델에 절대 토큰 항이 없으므로 성립하지
> 않는 주장이었다.

#### ✅ K2(a) 완료 — 보고서가 예측구간을 낸다

README는 "예측구간 = α 민감도 × run 분산 밴드(실측 ±30~46%)"라고 안내한다. 그러나 그 구간을
산출하는 `model.estimate_cell`(`cost_low`/`cost_high`/`pi_low`/`pi_high`)을 **`cli.py`가 한 번도
호출하지 않는다** — 호출처는 테스트뿐이고 `cli.py`에 `pi_low` 0건. 보고서는 `$143.91`이라는
**점추정만** 낸다. run 분산이 ±30~46%인데 사용자는 센트 단위 숫자를 본다.

- **(a) 구간 노출** — 계산 로직은 이미 있다. 보고서에 열만 추가하면 된다. **저비용·고효과.**
- **(b) α fit** — `calibrate.py:120`이 `alpha_default: 0.5` 하드코딩. 설계는 로그선형 fit이나
  fit하려면 **EP별 (δ, w) 관측**이 필요하고 현재 없다(§4.6). **데이터 선행.**

(a)만으로도 정직성이 크게 오른다.

**완료(`792fb38`, `b3822ab`):** 보고서가 `예측구간: $81 ~ $231`을 낸다. 구간은 **선택된
파티션 위에서** α=0/1로 재시뮬레이션해 구한다 — `estimate_cell` 비율을 이식하면 167개를 한
청크로 보는(peak_context가 w_hard의 3.4배인, 플랜이 스스로 거부할) 구성의 민감도를 쓰게 된다.
하한은 전부 run 분산이다 — `0<α<1`에서 `cost_low`는 점추정과 같아 α가 기여하지 않는다.
**(b) α fit은 여전히 미완**이며 EP별 관측이 선행이다.

#### ✅ K4 완료 — 크래시

`w_hard`가 낮아 모든 W_target frac이 실패하면 `best`가 `None`인 채 `plan.py:88` (`best.update`)에서
`AttributeError: 'NoneType' object has no attribute 'update'` (재현 확인:
`build_plan(..., w_hard=1000)`). 설계가 요구한 **로컬 재분할 루프**도 없어, 벽을 넘으면 재분할
대신 그 frac을 통째로 버린다. 작은 컨텍스트 모델을 지정한 사용자가 traceback을 본다.

#### ❌ K7은 결함이 아니다 (실행 검증)

`calibrate.py:115`가 `latency_s_per_turn = median(wall_s / turns)`로 **실측 총 wall에서**
fit한다. 따라서 `model.py:38`의 `turns × latency`는 **항등식**이며(실측 3개 run에서 정확히
일치), 그 wall에는 출력 스트리밍 시간이 **이미 포함**돼 있다. 설계의 `Σout/rate`를 더하면
**이중 계산**이 된다.

다만 여지는 있다 — 턴별 timestamp가 트랜스크립트에 있어 2항 분해를 fit할 수 있고(회귀 결과
턴 오버헤드 5.46s, 출력률 176 토큰/초, R²=0.40), `out/turn` 비율이 K에 따라 998→1525로
변하므로 외삽 정확도는 개선될 수 있다. 셀별 재fit이 필요한 별도 작업이며, **현재 구현이
틀린 것은 아니다.**

#### ✅ external_call 완료 — 구조적으로 항상 False였다

`EXTERNAL_CALL_TYPES`가 `SPRING_INFRA`의 부분집합이라 `_injected_types()`가 먼저 걸러낸다.
167 EP 전체에서 `external_call=True`가 **0건**(실측). 보고서의 external 열이 항상 비어 있다 —
모듈 독스트링의 "조용한 0 금지" 원칙을 그 모듈이 위반한다. 수정해도 **w_tokens는 불변**(외부
타입은 토큰을 더하지 않고 플래그만 세운다).

**완료(`792fb38`):** 필터를 `SPRING_INFRA - EXTERNAL_CALL_TYPES`로 바꿔 도달 가능하게 했다.

## 7. 관통하는 패턴 — 조용한 절반 구현

B단계 1·3·4번과 §4의 복잡도 축은 성격이 같다. **설계 문서에는 있는데 구현이 절반만 됐고, 그
절반이 조용히 빠져 있다.** α 민감도는 계산되지만 출력되지 않고, `out_rate`는 문서화됐지만
없고, `external_call`은 필드가 있지만 항상 False이고, 복잡도는 폐기됐지만 보고서는 여전히
"복잡도"라고 라벨한다. **코드만 보면 다 있어 보이는데 실제 경로엔 연결이 없다.**

본 세션에서 잡은 비결정성도 같은 부류다 — 테스트가 전부 깨져 있어서(결합 1) 아무도 안 돌려본
사이에 잠복했다. A단계에서 테스트를 살리자마자 hold-out·LOO 커버리지가 다시 돌기 시작했다.

**이 패턴은 문서를 읽는 사람도 감염시킨다.** 이 문서 초판이 그 증거다 — `controller_shared_tokens`가
생성만 되고 소비처가 0건인 것을 보고 "비용에서 누락됐다"고 단정했으나, 모델에 절대 토큰 항이
애초에 없으므로 누락될 것도 없었다(§3.4.1). 필드의 존재가 그것이 쓰여야 한다는 인상을 만들고,
"안 쓰인다 = 결함"이라는 추론을 유도한다. **코드를 읽고 결함을 주장하기 전에 그 값이 실제로
어디로 흘러가는지 실행으로 확인해야 한다** — 스케일 불변성 실험(모든 w를 2배 → 결과 불변)
한 번이면 초판의 1순위 오판을 막을 수 있었다.

그래서 **분리(A)가 순서상 먼저였다.** 테스트가 돌아야 개선(B·C)의 수치 변화가 의도된 것인지
사고인지 구분할 수 있다.
